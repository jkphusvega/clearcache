## Problem Statement

컴퓨터를 쓰다 보면 저장공간이 쌓인다. 목표는 그 공간을 **최대한 빠르고, 쉽고, 안전하게** 확보하는 것이다.

WizTree 같은 도구는 "무엇이 큰지"는 쉽게 알려준다. 하지만 실제로 큰 것은 대부분 `Users\AppData`, `Windows`, `Program Files`에 있어서, 사용자는 "이거 지워도 되나?"에서 막힌다. ClearCache는 이 질문에 답하고, 안전하게 확보하는 방법까지 제공한다.

폴더는 네 종류로 나누고 각각 다르게 처리한다. **v1 기준**이다.

| 분류 | 예 | v1 처리 |
| --- | --- | --- |
| (1) 바로 정리 가능 | AppData 캐시, Temp의 오래된 항목, 개발·AI 캐시 | 근거를 보여준 뒤 격리(같은 드라이브 안 rename)한다. **공간은 격리함에서 "완전 삭제"를 누를 때 확보된다**(앱 안의 버튼, 사용자가 누름). |
| (2) 공식 도구로 정리 | WinSxS, Windows 업데이트 캐시, hiberfil.sys, Windows.old, 메모리 덤프, WSL·Docker 디스크 | 파일을 직접 건드리지 않는다. 공식 방법을 설명하고 **딥링크(`ms-settings:` 등)와 복사할 수 있는 명령만** 제공한다. 앱은 관리자 권한으로 아무것도 실행하지 않는다. |
| (3) 앱 제거로 해결 | Program Files의 큰 폴더 | 어떤 앱인지(와 확인되면 마지막 실행 시점)를 알려주고 Windows 앱 제거 화면(`ms-settings:appsfeatures`)으로 안내한다. |
| (4) 건드리면 안 됨 | Windows 핵심 파일, 기타 Windows | 이유만 설명한다. |

"시스템 폴더 파일은 ClearCache가 직접 삭제·격리하지 않는다"는 원칙은 유지한다. 그 대신 시스템 폴더도 크기를 보여주고, "지워도 되나"에 대한 답과 공식 확보 방법을 제공한다.

**v1 이후 후보**(2주 사용 점검 뒤 결정): 공식 도구를 앱 안에서 관리자 권한으로 실행하는 기능. 사용자가 명시적으로 요청할 때 동작 하나마다 `ShellExecuteEx runas`로 권한을 받는다. WinSxS의 정확한 값을 얻는 DISM 분석 실행도 여기에 포함된다.

## What Makes This Cool

- **정직한 확보량.** 선택한 항목의 "지우면 N GB"는 검증된 값이다. 하드링크(uv, pnpm, WinSxS), NTFS 압축, 클라우드 파일을 반영한 `exclusive_bytes`로 계산한다. 검증되지 않은 값은 "최대치(미검증)"로 구분해 표시한다.
- **확보 영수증.** 완전 삭제 직전과 직후의 여유 공간을 재서 "예측 vs 실제"를 보여준다.
- **개발·AI 캐시 규칙 묶음.** Ollama 모델, Hugging Face, uv, pip, npm, pnpm, cargo, `.next`, `node_modules`를 특히 정확하게 다룬다. 소유자가 이 캐시들을 매일 쓴다.
- **되돌릴 수 있음.** 즉시 삭제하지 않고 격리한다. AI 판정은 기본 체크 해제다.

## Constraints

- Windows 전용이다(Tauri 2 + React/TS/Tailwind + Rust). 서버가 없다.
- **관리자 권한 없이 동작**해야 하고, v1은 관리자 권한을 받는 경로가 없다.
- 격리는 v1에서 C:만 한다. 다른 드라이브는 보기 전용이다.
- M2 환경 범위:
  - 다루는 것: 관리자가 아닌 계정, OneDrive로 옮겨진 폴더, 긴 경로, exFAT 이동식 드라이브
  - 다른 사용자 프로필과 `Program Files\WindowsApps`: "건너뜀(접근 거부)"만 표시
  - 나머지 환경 대응: M6
- **클라우드 전용 파일은 절대 열지 않는다.** `RECALL_ON_DATA_ACCESS`, `RECALL_ON_OPEN`, `OFFLINE` 속성인 파일은 열면 다운로드가 일어날 수 있다. 크기는 디렉터리 목록 정보만 쓰고, 이 파일들은 0바이트로 센다.
- **라이선스: MIT로 임시 결정.**
  - BleachBit(GPLv3)의 규칙은 참고만 하고 복사하지 않는다.
  - 규칙은 직접 작성하고, 출처가 필요하면 문서 링크로만 남긴다.
  - M3에서 규칙을 쓰기 전에 최종 확정한다.
- AI 전송 범위는 SPEC "3. AI 분류기"를 따른다(사용자 이름 `<USER>` 치환, 파일 내용 없음, 첫 호출 전 미리보기와 동의). 프로젝트·고객사 이름이 경로에 드러나는 문제는 **M5 설계 의무**로 둔다. 경로 일반화나 해시 여부를 M5 계획에서 정한다.

## Premises

1. 차별점은 판정(규칙 + AI 근거), 되돌릴 수 있는 격리, 오픈소스 신뢰다. 스캔 속도로 WizTree와 경쟁하지 않는다.
2. 스캔은 관리자 권한 없이 동작한다. v1은 `std::fs::read_dir` + `rayon`이다. MFT 직접 읽기(관리자 필요)는 v2에서 관리자 모드 가속 후보로 둔다.
3. 배포용이므로 서명된 설치 파일, 자동 업데이트, GitHub Releases 빌드를 설계에 포함한다(M6). 서명은 유료 인증서보다 **SignPath Foundation 같은 오픈소스 무료 서명 프로그램**을 먼저 검토한다. 한국 개인 개발자도 자격이 되는지는 M6에서 확인한다.
4. 다른 사람의 PC는 제각각이다. M2에서 다루는 범위는 위 Constraints와 같고, 나머지는 M6에서 다룬다.

## Cross-Model Perspective

Claude 서브에이전트(대화 맥락 없음, 같은 계열 모델)의 의견을 요약한다.

- **가장 멋진 버전: "확보 영수증"과 재생성 추적.** 재생성 추적은 "약 3일이면 다시 참"과 "한 번 지우면 끝"을 구분한다. 질문이 "안전한가"에서 "지울 가치가 있는가"로 바뀐다.
- **핵심 인용:** "you get stuck at 'can I delete this?'. ClearCache answers that question." 흥미의 중심은 스캔이 아니라 판정이다.
- **절반을 해 주는 기존 도구:** BleachBit CleanerML(참고만, GPL)과 pdu·dua-cli(Rust 스캐너). 직접 만들 절반은 하드링크 반영 확보량, 네 종류 분류, 격리·복원, 개발·AI 규칙, 근거 설명 화면이다.
- **정확도 제안:** 파일 ID와 링크 수로 중복을 제거하고, 디스크상 크기는 `GetCompressedFileSizeW`로 잰다. uv·pnpm 캐시는 격리해도 확보량이 약 0일 수 있다. 동기화 폴더를 격리하면 클라우드에서 삭제된다.
- **공식 도구와 앱 제거의 함정:**
  - `DISM /ResetBase`는 기본으로 제안하지 않는다.
  - `powercfg /h off`보다 `/h /type reduced`를 먼저 제안한다.
  - cleanmgr 대신 저장소 센스로 연결한다.
  - "마지막 사용"은 절대 "사용 안 함"으로 표시하지 않는다.
- **교차 검토 결론:**
  - 고유 바이트와 동기화 폴더 격리 금지를 채택한다.
  - CLI를 따로 먼저 만드는 대신 core 라이브러리와 테스트용 CLI를 함께 둔다.
  - 재생성 추적은 M5 이후 후보로 둔다.

## Approaches Considered

- **A. 최소 변경:** 알려진 시스템 하위 폴더의 겉보기 크기만 추가하는 안. 하드링크 때문에 확보량이 부풀려져서 채택하지 않았다.
- **C. 카탈로그 우선:** 알려진 경로 약 60개를 먼저 보여주는 안. 목록 밖의 큰 폴더가 늦게 보이고 M3 규칙을 M2로 당겨야 해서 채택하지 않았다. "첫 화면은 네 종류 카드"라는 아이디어는 M3 화면에 반영한다.

## Recommended Approach — B. 확보량 계산 핵심

### 구조

- Rust `core` 라이브러리(scan, attrs, policy, accounting)를 두고, 테스트용 CLI(`scan --target <id> --json`)와 Tauri 커맨드가 같은 코드를 쓴다.
- 핵심 라이브러리를 따로 두면 WizTree와 숫자를 비교해 검증하기 쉽고, 포트폴리오로 설명하기도 쉽다.

### 숫자 모델

- **`logical_bytes`**: 모든 폴더에 계산한다. 디렉터리 목록 정보(`FindFirstFile`/`DirEntry::metadata`)의 파일 크기를 합한 값이고, 파일을 열지 않는다. 화면에는 "최대치(미검증)"로 표시한다.
- **`exclusive_bytes`**: 이 폴더를 지웠을 때 실제로 비는 디스크 공간이다.
  - **정의:** 범위(scope)는 해당 폴더와 그 하위 전체다. 파일의 디스크상 크기(`GetCompressedFileSizeW`)는 **범위 안에서 본 그 파일의 링크 수가 `nNumberOfLinks`와 같을 때만 한 번** 센다. 링크가 범위 밖에도 있으면 0으로 세고, 그 크기를 `shared_bytes`로 따로 보고한다.
  - 부모 폴더와 자식 폴더는 각자의 범위로 따로 계산한다. 자식의 exclusive 합이 부모 exclusive와 같다는 보장은 없다.
  - **언제 계산하나:**
    - 허용 목록 폴더: 스캔할 때 바로 계산한다. 목록은 Windows 알려진 하위 폴더, 하드링크를 쓰는 캐시 루트(uv 캐시, pnpm 저장소)다.
    - 그 밖에 선택 가능한 폴더: 사용자가 **체크하거나 펼칠 때** 계산한다. 규칙에 걸린 `node_modules` 등이 해당한다. 계산 중에는 "확인 중…"을 표시한다.
    - 격리 버튼의 합계는 exclusive가 확인된 항목만 확정 값으로 쓰고, 나머지는 "최대치"로 따로 표시한다.
  - **파일 여는 방식:**
    - 접근 권한은 `FILE_READ_ATTRIBUTES`만 요청한다.
    - 공유 모드는 `FILE_SHARE_READ | FILE_SHARE_WRITE | FILE_SHARE_DELETE`다.
    - 플래그는 `FILE_FLAG_OPEN_REPARSE_POINT | FILE_FLAG_BACKUP_SEMANTICS`다.
    - 클라우드 전용 속성인 파일과 동기화 루트 안의 파일은 **열지 않는다**(속성은 목록 정보로 먼저 판별).
    - 열기에 실패하면(공유 위반, 접근 거부) 그 파일은 logical 크기로 세고 폴더에 "일부 미검증 N개"를 표시한다.
- **WinSxS:** exclusive 값은 "Windows와 공유되지 않는 파일 N GB (전부 확보 가능한 것은 아님)"라는 **중립 라벨**로 표시한다. "확보 가능"이라는 라벨은 M2에서 내 PC의 DISM `AnalyzeComponentStore` 값과 비교해 근거가 생길 때만 쓴다. 정확한 확보량은 "관리자 PowerShell에서 이 명령으로 확인" 카드로 안내한다.

### 시스템 항목 매핑 ("측정 안 함" 결정을 바꿈)

모든 항목은 **보호 대상**이라 선택할 수 없다. 크기는 디렉터리 목록 정보로 얻고, 루트 파일도 열지 않는다.

| 항목 | 측정 | 분류 | v1 안내 |
| --- | --- | --- | --- |
| `Windows\WinSxS` | logical + exclusive(중립 라벨) | (2) | 저장소 센스 딥링크, DISM 분석·정리 명령 복사(`/ResetBase` 제외, 부작용 설명) |
| `Windows\SoftwareDistribution\Download` | logical | (2) | 저장소 센스 → 임시 파일(Windows 업데이트 정리) |
| `Windows\Installer` | logical | (4) | 설명만: 지우면 앱 복구·제거가 깨짐. 해당 앱을 제거해야 줄어듦 |
| `Windows\Temp` | logical(접근 가능한 만큼) | (2) | 저장소 센스 → 임시 파일 |
| `Windows\Minidump`, `Windows\LiveKernelReports`, `C:\Windows\MEMORY.DMP` | logical | (2) | 저장소 센스 → 시스템 오류 메모리 덤프 파일 |
| `C:\Windows.old` | logical(접근 가능한 만큼) | (2) | 저장소 센스 → 이전 Windows 설치 |
| `hiberfil.sys` | 목록 정보 크기 | (2) | `powercfg /h /type reduced` 먼저 안내(빠른 시작 유지), `/h off`는 부작용 설명과 함께 |
| `pagefile.sys`, `swapfile.sys` | 목록 정보 크기 | (4) | 설명만: 가상 메모리. 설정 변경은 권장하지 않음 |
| 기타 Windows | 측정 안 함 → "스캔되지 않은 용량"에 포함 | (4) | 설명만 |
| `Program Files`, `Program Files (x86)` 하위 앱 폴더 | logical | (3) | 앱 연결 + 앱 제거 화면 딥링크 |
| `Program Files\WindowsApps` | 건너뜀(접근 거부) | (3) | `ms-settings:appsfeatures` 딥링크 |
| WSL·Docker `.vhdx` | logical(목록 정보) | (2) | 압축(Optimize-VHD / `wsl --manage --set-sparse`) 안내. **절대 격리하지 않음** |

### 판정 모델 (M3)

- 등급과 별도로 처리 방식 `action` 필드를 둔다: `quarantine` / `official_tool` / `uninstall_app` / `explain_only`.
- 규칙 묶음은 Windows 기본 묶음과 개발·AI 묶음이다.
- **선택 정책:** SPEC을 따른다.
  - 규칙 DB "안전" 항목만 기본 체크한다.
  - 보호 대상이 아닌 다른 폴더(사용자 데이터·모름)는 선택할 수 있지만 경고 모달을 거친다.
  - `action`이 `quarantine`이 아닌 항목은 선택할 수 없다.
  - 확보량이 "계산 중"이거나 계산이 취소된 폴더는 선택·격리할 수 없고, 예상 확보량 합계에도 넣지 않는다(D13). 체크박스를 누르면 계산이 시작되고, 값이 나오면 선택된다.
- **앱 연결:** Uninstall 레지스트리(HKLM, HKLM WOW6432Node, HKCU)의 `InstallLocation`으로 연결하고, 비어 있으면 `DisplayIcon`·`UninstallString`의 폴더로 보완한다. Steam 라이브러리는 Steam으로 안내한다.
- **마지막 실행:** v1의 데이터 소스는 HKCU `UserAssist`(ROT13, 관리자 없이 읽힘)뿐이다. 설치 폴더 안의 exe 경로와 일치하는 기록이 있으면 "시작 메뉴·탐색기에서 마지막 실행: 날짜"로 표시하고, 없으면 "알 수 없음"으로 표시한다. "사용 안 함"이라고는 절대 표시하지 않는다. BAM은 Open Question이다.

### 격리와 영수증 (M4)

- **위치와 보관:** SPEC을 따른다.
  - 위치는 `C:\ClearCache_Quarantine\<날짜>\<id>`이고, 기록은 SQLite `quarantine` 테이블에 남긴다.
  - 7일이 지나면 알림만 띄우고 자동 삭제는 하지 않는다.
  - 격리함 용량은 상단에 표시한다.
  - 스캐너는 격리함을 제외한다.
- **이동 방식:**
  - 폴더 전체를 `rename` 한 번으로 옮긴다. `MoveFileExW`에 복사 허용 플래그를 넣지 않으므로 다른 볼륨이면 **실패하고 복사하지 않는다**. 옮기기 전에 원본과 대상의 볼륨 번호가 같은지도 확인한다.
  - rename이 실패하면(파일 사용 중, 권한) 아무것도 옮기지 않고 "사용 중"으로 표시한다. 부분 이동은 없다.
  - 알려진 앱의 캐시(브라우저, Ollama, Docker, IDE)는 격리 전에 해당 프로세스가 실행 중이면 "앱을 먼저 종료하세요"를 안내한다.
- **리파스 포인트:** 스캐너는 따라가지 않는다(SPEC). 리파스 포인트 폴더 자체(정션, 심볼릭 링크, 마운트 지점)는 v1에서 **선택할 수 없다**.
- **동기화 루트 보호:** OneDrive뿐 아니라 **등록된 모든 클라우드 동기화 루트**가 대상이다.
  - 감지 방법:
    - `HKLM\...\Explorer\SyncRootManager` 하위 키(관리자 없이 읽힘)
    - `HKCU\Software\Microsoft\OneDrive\Accounts\*\UserFolder`(여러 계정)
    - `%OneDrive%` 계열 환경 변수
    - 알려진 폴더 리디렉션 위치
  - 이 안의 폴더는 **격리하지 않고**, 파일은 **열지 않는다**.
- **복원:** SPEC의 복원 충돌 정책을 따른다(덮어쓰지 않고 "기존 유지·격리본 삭제 / 나란히 복원 / 취소" 중 선택). 복원 직전에 안전 규칙을 다시 검사한다. 원래 위치가 이제 보호 대상이나 동기화 루트 안이면 복원을 거부하고 다른 위치를 고르게 한다.
- **완전 삭제와 영수증:**
  - 공간은 격리 시점이 아니라 **완전 삭제 시점**에 확보된다. 격리 직후 영수증은 "지금 확보 0 · 비우면 예상 N GB"로 표시한다.
  - 완전 삭제는 **직전·직후**의 `GetDiskFreeSpaceEx` 차이를 실제 확보량으로 기록한다.
  - 1 GB 미만 동작은 오차 판정에서 제외한다(다른 시스템 활동 때문).
  - 확보량이 "계산 중"이거나 계산이 취소된 폴더는 선택·격리할 수 없고, 예상 확보량 합계에도 넣지 않는다(D13).
  - 측정 중 다른 활동(업데이트, 페이지 파일, 동기화)이 있을 수 있다는 주의를 영수증에 적는다.
- **공식 도구 카드:** 딥링크와 복사할 수 있는 명령만 제공한다(위 매핑표).

### R2-1 — completeness

**Problem**

> The quarantine move behavior is now specified: one whole-folder rename, nothing moved on failure, shown as '사용 중', and a running-process pre-check for known apps. But the unit tests do not cover it. The safety rules section limits test targets to '속성 판별, 경로 판정, 볼륨 비교 함수', and the Success Criteria safety list has no rename-failure, no-partial-move or process pre-check test.

**Remedy**

### R2-2 — completeness

**Problem**

> Reparse points are handled for scanning, and a reparse-point folder itself is not selectable. But a normal folder that is selected can contain reparse points, such as the junctions in pnpm node_modules or Hugging Face snapshot symlinks. Nothing says how '완전 삭제' walks such a quarantined folder. A recursive delete that follows a junction or symlink would delete the target: the pnpm store, the HF blobs, or data outside C:.

**Remedy**

> State that permanent delete removes nested reparse points as links without following them, never recursing into their targets. Add this to the safety rules and to the unit tests: a quarantined folder containing a junction and a symlink to an outside directory, where the outside directory survives.

### R2-3 — consistency

**Problem**

> exclusive_bytes is computed per folder scope, and the quarantine button's total adds up the selected items' exclusive values. That total is wrong in two ways. Nested selections (a parent and its child both checked) are double-counted. Files hard-linked only between two selected items (a pnpm store plus project node_modules, or a uv cache plus a venv) count as 0 in each item, but deleting both frees them. This contradicts '선택한 항목의 "지우면 N GB"는 검증된 값' and can break the 10% success criterion for multi-item deletes.

**Remedy**

> Define the selection total as exclusive_bytes over the union scope of all selected items: remove nested duplicates, and count a file when all of its links fall within the union. Apply the same rule to the '비우면 예상 N GB' prediction when several quarantined items are emptied together.

### R2-4 — clarity

**Problem**

> When file opens fail, a folder mixes exclusive-verified and logical-fallback bytes, shown as '일부 미검증 N개'. The document does not say whether that folder counts as 'exclusive가 확인된 항목' (a confirmed value in the quarantine total) or goes to the '최대치' bucket. It also does not say whether such items are in or out of the 10% prediction-error measurement.

**Remedy**

> Define how a partly unverified folder is shown and totaled, for example by splitting it into verified bytes plus an unverified remainder shown under '최대치'. Say whether it is included in the success-criterion error check.

### R2-5 — feasibility

**Problem**

> The open mode is carefully specified: FILE_READ_ATTRIBUTES, full sharing, OPEN_REPARSE_POINT and BACKUP_SEMANTICS. But on-disk size comes from GetCompressedFileSizeW, which takes a path and opens the file itself. That open bypasses the stated flags: it can follow a symlink file and fail with sharing violations. It also doubles the per-file opens that the Open Question on node_modules speed is concerned about.

**Remedy**

> Get on-disk size from the same handle, for example GetFileInformationByHandleEx with FileCompressionInfo or FileStandardInfo.AllocationSize, chosen to be correct for NTFS-compressed and sparse files. Alternatively, state the reparse and sharing behavior of the path-based call and its fallback.

### R2-6 — completeness

**Problem**

> Protection is defined for the protected item itself: a .vhdx, a sync root, a reparse-point folder, the system folders. It is not defined for a selectable ancestor that contains one. Under the selection policy, any non-protected folder can be selected after a warning modal. So a user could quarantine %LOCALAPPDATA%\Docker or a WSL distro's LocalState folder that holds a registered .vhdx, or a folder that contains a nested sync root. The move would take the protected item with it.

**Remedy**

> Add a rule that a folder cannot be selected, or must be refused at quarantine time, when its subtree contains a protected item: a WSL/Docker disk, a sync root, the quarantine root, or a system-protected path. Say how this is detected, and add a unit test.

**Problem**

Between the scan and the button press, the path may have become a reparse point, moved into a new or newly registered sync root, gained cloud-only files, or changed contents enough to invalidate its rule match.

**Remedy**

**Remedy**

**Problem**

### R2-13 — completeness

**Problem**

**Remedy**

**Problem**

**Remedy**

### R2-15 — feasibility

**Problem**

For MSI and many installers these point to C:\Windows\Installer\{GUID}\..., to msiexec.exe in System32, or to a shared vendor parent folder. Without a guard, apps would be linked to the wrong folder or to a shared one.

**Remedy**

> Accept a fallback-derived folder only when it is under Program Files or Program Files (x86), or under a known per-user app root, and is not a shared vendor parent. Otherwise leave the app unlinked.
